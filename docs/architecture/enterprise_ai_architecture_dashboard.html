Architectural principles

  • Reusable by design: shared services, configurable domain adapters.
  • Model-agnostic: provider abstraction and controlled model routing.
  • Knowledge separated: business knowledge lives in governed data stores, not assumed model memory.
  • Secure by default: tenant isolation, least privilege and data minimization.
  • Measured delivery: evaluate quality, latency, cost and risk before release.
Key decision: Do not create one fine-tuned model per product automatically. Identify reusable tasks and prove that fine-tuning improves a measured outcome.

Choose the right pattern

Prompting

Change instructions

Use when behaviour can be achieved through clear instructions, examples and structured output constraints.

RAG

Use current enterprise knowledge

Use when answers depend on private, changing or source-attributable documents and records.

Fine-tuning

Adapt task behaviour

Use when representative examples show a persistent behaviour gap that prompting alone cannot economically close.

Control plane vs data plane

Control plane: policies, model approvals, prompt versions, access rules, evaluation thresholds and deployment configuration.

Data plane: runtime requests, retrieval, inference, tool execution and business-system interactions.

Multi-tenancy approach

Resolve tenant and user identity at the gateway. Enforce tenant-scoped retrieval filters, storage boundaries, encryption, quotas and audit records. Never rely on prompt instructions as an authorization boundary.

Reusable RAG components

  • Connectors and ingestion scheduler
  • Document parser and OCR adapter
  • Chunking and embedding service
  • Vector / keyword retrieval abstraction
  • Reranking and context assembly
  • Citation and answer-quality evaluator

Design decisions to document

  • Chunk size and overlap by document type
  • Embedding model and index version
  • Hybrid vs vector-only search
  • Metadata filters and document-level ACLs
  • Freshness SLA and deletion propagation
  • Fallback when evidence is missing or weak
Critical security rule: Apply authorization filters before retrieved content is sent to the LLM. A model must not receive documents the requesting user is not permitted to access.

Model adaptation methods

SFT Supervised fine-tuning on curated input-output examples.

LoRA Parameter-efficient adaptation using low-rank trainable updates.

QLoRA Quantized base model plus LoRA to reduce training memory requirements.

Preference optimization Optimize response preferences where suitable preference data and infrastructure exist.

Where agents help

  • Multi-step workflows across systems
  • Tasks requiring dynamic tool selection
  • Coordinating retrieval, extraction and validation
  • Escalation to human review for exceptions

Where deterministic code is better

  • Interest, premium or eligibility calculations
  • Permission checks and policy enforcement
  • Transaction posting and irreversible actions
  • Exact business rules and threshold validation

Security, governance & operations

Controls must apply across data ingestion, retrieval, inference, tools and model lifecycle.

Non-functional requirements

Security & privacy

  • SSO, OAuth/OIDC, RBAC/ABAC and least privilege
  • Tenant and document-level access enforcement
  • Encryption in transit and at rest; secrets vault
  • PII detection, masking and retention controls
  • Prompt injection and unsafe content defenses
  • Tool allowlists, scoped credentials and approval gates

Responsible AI & model risk

  • Use-case risk classification and documented intended use
  • Representative evaluation datasets and acceptance thresholds
  • Bias, robustness, hallucination and toxicity testing as applicable
  • Human oversight for consequential decisions
  • Model cards, data lineage and change approvals
  • Incident response, rollback and periodic revalidation

Governance principle: An LLM response is not authorization. Validate identity, entitlements, business rules and transaction limits in trusted application services before exposing data or executing actions.

Project-level implementation roadmap

A phased delivery plan to turn the reference architecture into a working enterprise platform.

Suggested delivery sequence
Phase 1 · Foundation

Platform skeleton

  • Define target use cases, personas and success metrics
  • Set up repo, CI/CD, environments and secrets
  • Implement API gateway, identity and tenant context
  • Build model-provider abstraction and logging
Phase 2 · Knowledge

Reusable RAG service

  • Build document ingestion and parsing connectors
  • Add chunking, embeddings and vector search
  • Enforce document ACL filters
  • Add citations, evaluation and freshness monitoring
Phase 3 · Model factory

Adaptation pipeline

  • Define use-case intake and baseline evaluation
  • Prepare governed training and validation datasets
  • Run approved SFT / LoRA experiments where justified
  • Register, approve, deploy and roll back versions
Phase 4 · Orchestration

Agent workflows

  • Implement workflow orchestration and tool contracts
  • Integrate business APIs with scoped credentials
  • Add deterministic validations and human approvals
  • Test failure paths, retries and idempotency
Phase 5 · Domain rollout

Pilot and scale

  • Start with one bounded, low-risk use case
  • Prove quality, security, latency and cost
  • Package reusable domain configuration
  • Onboard additional divisions incrementally
Phase 6 · Operate

Continuous improvement

  • Monitor model, retrieval and agent performance
  • Review drift, incidents and user feedback
  • Re-evaluate after model, data or prompt changes
  • Retire stale versions and unused components
